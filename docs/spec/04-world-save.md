# 仕様 04: 無限ワールドと保存

対象クレート: `charon-world` (マイルストーン M5)。先に仕様 01、02 を読むこと。

## 1. チャンクの状態

```
未生成 ──生成──▶ 読み込み済み ◀──読み込み── 保存済み (ディスク上)
                     │                          ▲
                     └────────退避──────────────┘
```

`World` (仕様 01 §5) が持つのは「読み込み済み」のチャンクだけである。存在しないチャンクを読むと
`BOUNDARY` が返るので、読み込み範囲の端は自動的に壁になる。

## 2. 読み込みと退避

カメラ (複数可) ごとに、中心チャンクからの距離で 2 つの範囲を決める。

| 範囲 | 距離 (チェビシェフ距離) | 動作 |
|---|---|---|
| 読み込み範囲 | `load_radius` 以内 | チャンクが必ず存在する |
| 退避範囲 | `load_radius + 2` より外 | 保存して `World` から外す |

間の 2 チャンクは「何もしない」帯で、境界を行き来しても読み書きが繰り返されないようにする。

毎 tick の処理:

1. 読み込み範囲にあって存在しないチャンクを、カメラに近い順に「要求リスト」に入れる。
2. 要求を作業スレッドに渡す。作業スレッドはディスクから読む。なければ生成する (§4)。
3. 完成したチャンクを受け取り、`World` に入れる。1 tick に受け取るのは最大 4 個。
4. 退避範囲のチャンクを `World` から外し、保存のために作業スレッドへ渡す。1 tick に最大 4 個。

**決定性のための規則**: チャンクが `World` に入る tick は、スレッドの速さで変わってはいけない。
そのため「要求した tick + 固定の遅延 (既定 30 tick)」に必ず入れる。その時点で完成していなければ、
メインスレッドは完成を待つ (一瞬止まるが、結果は変わらない)。

スレッドのない環境 (wasm) では、要求をその場で同期的に処理する。挿入の tick は同じ規則に従う。

## 3. 保存形式

### ファイル配置

```
saves/<world_name>/
    world.ron                 seed、tick、形式のバージョン、材質名の一覧
    regions/r.<rx>.<ry>.bin   32×32 チャンクを 1 ファイルにまとめる (rx = cx >> 5)
    bodies.bin                剛体 (M6 以降)
```

### リージョンファイル

```
ヘッダー (固定長):
    magic: [u8; 4] = b"CHRN"
    version: u16 (リトルエンディアン。現在 1)
    予約: u16 = 0
    表: 1024 個の { offset: u32, length: u32 }   # 添字 = (cy & 31) * 32 + (cx & 31)。length 0 は未保存
本体: 各チャンクの圧縮済みデータを後ろに並べる
```

書き換え時は、新しいデータをファイル末尾に足して表を更新する。ファイルの無駄な領域が半分を超えたら、
詰め直した新しいファイルを別名で書き、`rename` で置き換える。
**元のファイルを直接上書きしない** (書き込み中に落ちてもデータが壊れないようにするため)。

### チャンクのデータ (圧縮前)

```
palette_len: u16
palette: palette_len 個の u16      # world.ron の材質名一覧への添字
cells: 4096 個の { palette_index: u8 または u16, flags: u8, shade: u8, temp: i16, vy: i8, life: u8 }
```

- `palette_len <= 256` なら `palette_index` は `u8`、それ以外は `u16`。
- `FLAG_BODY` のセルは `EMPTY` として保存する (剛体は `bodies.bin` に別に保存する)。
- `FLAG_PARITY` は 0 にして保存する。
- 圧縮は LZ4 (`lz4_flex` クレート)。空のチャンクはほぼ 0 バイトになる。
- 数値はすべてリトルエンディアン。`Cell` を `transmute` で書き出してはいけない
  (フィールドごとに書く。形式がメモリ配置に依存しないようにするため)。

### 材質 ID の変化への対応

保存時に、`world.ron` へ材質名の一覧を書く。読み込み時は、名前から現在の `MaterialId` に引き直す。
これにより、`materials.ron` に材質を足したり順番を変えたりしても、古いセーブが読める。
名前が見つからない材質は `EMPTY` に置き換え、警告をログに出す (エラーにして読めなくはしない)。

### バージョン

`version` が現在より新しいファイルは、読まずにエラーにする。古いバージョンは、
`fn migrate_v1_to_v2(...)` のような関数を順に適用して読む。形式を変えるときは必ず `version` を上げ、
古い形式のファイルをテスト用に `tests/fixtures/` に残す。

## 4. ワールド生成

```rust
pub trait ChunkGenerator: Send + Sync {
    /// `pos` のチャンクを作る。同じ `seed` と `pos` に対して、必ず同じ結果を返すこと。
    /// 他のチャンクの状態を読んではいけない。
    fn generate(&self, seed: u64, pos: ChunkPos, materials: &MaterialTable) -> Chunk;
}
```

M5 で用意する実装は 2 つだけ。

- `FlatGenerator`: y が 0 以上は石、未満は空。テスト用。
- `NoiseGenerator`: 地表の高さを 1 次元のノイズで、洞窟を 2 次元のノイズのしきい値で決める。
  地表から 8 セルは土、その下は石。ノイズは `rng::hash` を格子点の値に使う値ノイズを自前で実装する
  (外部のノイズクレートに決定性を預けない)。

バイオームや構造物は M8 で扱う。

## 5. 必須テスト

| テスト | 内容 |
|---|---|
| `roundtrip` | 乱数で埋めたチャンクを保存して読むと、`FLAG_PARITY` と `FLAG_BODY` を除いて一致する |
| `empty_chunk_is_small` | 空のチャンクの圧縮後が 64 バイト以下 |
| `material_reorder` | 材質の順番を変えた `MaterialTable` で読んでも、各セルの材質名が保存時と同じ |
| `unknown_material_becomes_empty` | 削除された材質はエラーにならず `EMPTY` になる |
| `crash_safety` | 書き込みを途中で打ち切ったファイルがあっても、以前のデータを読める |
| `newer_version_is_rejected` | `version` が大きいファイルはエラーになる |
| `walk_away_and_back` | カメラを 100 チャンク動かして戻ると、元の場所の `state_hash` が退避の直前と同じ |
| `streaming_is_deterministic` | 作業スレッドに乱数の遅延を入れても、毎 tick の `state_hash()` が同じ |
| `generator_is_pure` | 同じ `seed` と `pos` で 2 回生成すると一致する。生成の順番を変えても一致する |
