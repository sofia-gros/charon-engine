# Charon Engine: 製品ゲームとして必要な機能・改善点・性能の総合報告

対象: v0.0.7 (M19〜M27 を実装・自動テストした状態)。
目的: 「落下砂ゲームのための Rust 製エンジン」から、「Terraria 型の商品ゲームを出せるエンジンとデモ」へ進むために、足りないもの・直すべきもの・速くすべきものを、**網羅的に**挙げる。

この文書は、次の順に書く。

1. 要旨
2. 現状の把握 (規模・構成・テストの状態・できていること)
3. この報告の方法と限界
4. 機能の不足 (領域別、約 20 領域)
5. 既知の簡略化と、すでに分かっている不具合・懸念
6. 品質・保守性の改善 (設計・コード・テスト・文書・工程)
7. 性能: 現状の分析・計測の方針・施策・予算
8. リスクと判断が必要なこと
9. 提案するロードマップ (M28 以降)
10. 付録 (未実装の一覧、用語、仕様との対応)

「必須」「推奨」「任意」の印は、**商品としてリリースするために**どの程度必要かを示す。
必須 = ないと商品として成立しない。推奨 = ないと評価・継続率が大きく下がる。任意 = あると良い。

## 1. 要旨

- エンジンの核 (セル・熱・反応・剛体・描画・保存・並列化) は、M12 までに実装され、決定性と `unsafe` なしを保ったまま 500 以上の自動テストで守られている。M19〜M27 で、ブロック・アイテム・Terraria 型の操作・戦闘・冒険の世界・敵とボス・復活・範囲の外の液体と気体の移動を足し、**「遊べる骨格」は一通りそろった**。
- ただし、**人が通して遊んで確かめた回数は 0 回**である (M19 以降)。自動テストと GPU の描画テストは通っているが、操作の感触・見た目・音・バランスは未検証で、商品の品質はここで決まる。**最優先は実機の通しプレイ**。
- 機能面の最大の穴は、(1) セーブの最後の配線 (持ち物・装備の保存が App につながっていない)、(2) 建築の「機能ブロック」と背景の壁 (作業台・箱・ドア・松明・壁)、(3) 敵の知能とボスの行動、(4) 日本語・BGM・昼夜・チュートリアルという「体験の層」、(5) 署名つきの配布・権利の確認、(6) マルチプレイの組み込み、である。
- 性能面では、100 万セル / tick で約 35〜41 ms (目標 8 ms) が未達で、とくに**溶岩の熱が眠らない**ことが、深い洞窟の多い冒険の世界で効く。ただし、商品では「画面のまわりの更新するセル」だけが問題になるので、目標の定義の見直しと、計測の整備 (実ゲームの場面での tick 時間の分布) が先にある。
- 進め方の提案は §9。大づかみには、実機の通しプレイ → セーブ → 熱の休眠 → 建築の機能 → 敵 → 体験の層 → 配布、の順で、v0.1.0 を目指す。

### 2.2 できていること (商品の観点)

- **世界**: 粉体・液体・気体・熱・反応・燃焼・剛体。決定的 (同じ seed と入力で、並列の有無によらず同じ結果)。休眠と更新距離 (コールドフリーズ)。範囲の外の液体の落下と気体の上昇 (M27)。
- **プレイヤー**: 2×3 ブロック (16×24 セル) の体、1 ブロックの自動の段差乗り越え、コヨーテタイム、ジャンプの先行入力、ワイヤーフック、浮遊 (燃料)、体力・息・マナ、状態異常 (燃える・濡れる・毒)、死亡と 3 秒後の復活。
- **建築**: 8×8 セルのブロック (置く・押し出す・壊す・粉の崩れ・64 セルからのクラフト)。
- **アイテム**: `items.ron` のデータ駆動、持ち物・ホットバー・クラフト・装備 5 枠・自動装備・保存 (名前で保存)。
- **戦闘**: 近接・弓・杖、防御・耐性、ダメージの種類、ノックバック、火の玉 (火の筋・発火・燃え広がり)。
- **敵**: 武器・防具を持つ敵 (自動装備)、骸骨・弓兵・魔術師・ゴーレム (ボス)、戦利品、ボスの体力バー、自動のスポーンと削除。
- **世界の生成**: 丘・バイオーム・池・洞窟・立て坑・鉱石・地下の水と溶岩・ブロックのダンジョンと家・底の境界。
- **操作**: Terraria Android 型のタッチ操作 (固定スティック・使うボタンのカーソル・スマートカーソル・フックのスティック・ホットバー)、デスクトップのキーボード・マウス・ゲームパッド。
- **基盤**: データ駆動 (RON)、MOD (RON + Rhai スクリプト)、`Game` トレイト、音のミキサー、Lockstep と TCP 中継 (組み込み前)、リリースの自動化 (v* のタグで Windows zip と Android apk)。

## 3. この報告の方法と限界

- **根拠**: コードと仕様の読み直し、M19〜M27 の実装中に見つけた制約・簡略化、自動テストの結果、既存の計測 (`docs/BENCHMARKS.md`)、GPU の描画テストの画像。
- **限界**: 実機での通しプレイ、ストアの審査基準、ライセンスの法的な判断、他社製品との比較実験は含まない。「Terraria と同じ」と書く箇所は、公開されている仕組みの一般的な理解に基づく。数値 (ダメージ・確率・間隔) は**仮の値**で、通しプレイで決める。
- **「必須」の判断**は、一人で作る個人開発の商品 (無料から低価格のインディー) を想定している。大規模な運営・課金・ライブサービスは対象外。

## 4. 機能の不足 (領域別)

### 4.1 世界・シミュレーション

**現状**: §2.2 のとおり。

**不足と提案**

1. **背景の壁 (必須)**: 現在、世界は「前景のセル」だけで、家やダンジョンの内側も外と同じ暗さ・同じ見た目になる。Terraria の「壁」(プレイヤーの後ろに置く板) に当たるものがない。
   - 提案: 背景レイヤーをセルの別の層 (1 セル 2 バイト程度、材質 ID のみ) として持つ。`charon-render` には `background_pass` がすでにあるので、描画の土台はある。保存は、チャンクの隣に背景の配列を持つ (版を上げる)。壁を置く・壊す・クラフトは、ブロックと同じ操作 (置くとき、背景のセルだけを書く)。
   - 光との関係: 壁のある部分は暗くする (洞窟・家の内側の暗さ)。光の計算は、前景の発光と壁の遮蔽を使う。
2. **光源 (必須)**: 材質の `emission` (溶岩・火) だけが光る。松明・ランタン・光る鉱石・光る苔・発光するエンティティ (魔術師・火の玉) がない。M23 の火の玉は、火のセルが光ることで代用している。
   - 提案: 光を出すブロック (松明) を `items.ron` と材質 (`emission` を持つ固体) で用意する。エンティティに「光の半径と色」を持たせ、描画に渡す (動く光)。
3. **昼夜・時刻・天候 (推奨)**: 空の色・環境光・星・雲・雨・雪がない。`DEMO_CLEAR` / `DEMO_AMBIENT` が固定。
   - 提案: ワールドの tick から時刻を導く (1 日 = 例えば 10 分)。空の色は時刻で補間。夜は敵の出現を増やす (§4.5)。雨は、天井のない場所にだけ水のパーティクル (セルではなく描画のみ) を出し、地面で少量の水を足す。バイオームによって雪。
4. **範囲の外の世界の「経過」(推奨)**: M27 で液体の落下と気体の上昇は入れたが、**植物の成長・火の燃え広がり・水の広がりは止まったまま**である。プレイヤーが戻ったとき、「遠くで燃えていた火」は止まっている。
   - 提案: 範囲の外で、固体の燃焼を粗く進める (燃えている木のセルを、一定 tick で灰にする)。ただし、シミュレーションの結果が変わるので、仕様 02 §9 に書いて、テストで決定性を守る。
5. **水の広がり (推奨)**: M27 の粗い落下は「落下だけ」で、水が落ちた先で広がらない。範囲の外で水が積もったとき、1 本の柱になる。
   - 提案: 落下が止まったセルについて、左右の空きへ 1〜数セルだけ動かす (粗い広がり)。大きな水たまりを作るには、数 tick に 1 回の横移動で足りる。
6. **溶岩・水・油の相互作用の調整 (推奨)**: 反応の数は少ない (水 + 溶岩、酸 + いくつか)。Terraria 型として、黒曜石 (水 + 溶岩)、草の成長、氷の融解の連鎖、爆発物 (火薬・TNT)、ガスの爆発 (メタン + 火) の調整を足す。
7. **世界の端 (任意)**: 横には無限、縦は底の境界。上限 (宇宙) はない。表面より上の高さの上限・世界の幅の上限 (巻き戻し) を決めるなら、仕様 04 に書く。
8. **大きな構造物のストリーミング (推奨)**: 家やダンジョンは、区画 (256×192 や 192 列) の内側に収まる設計で、他のチャンクを参照せずに作れる。これより大きい構造物 (町・巨大ダンジョン) は、今の方式では作れない。複数の区画にまたがるときの、決定的な生成の仕組み (構造物の「アンカー」を決めて、チャンクごとに切り取る) が要る。
9. **世界のサイズ設定と「世界を選ぶ」画面 (推奨)**: ワールドの名前・サイズ・seed・難易度を選んで作る画面がない (今は Singleplayer と Random Seed のみ)。
10. **溶岩の熱の休眠 (必須、性能)**: §7 を参照。

### 4.2 地形生成 (冒険の世界)

1. **見た目の多様性 (必須)**: 今は 3 バイオーム (森・砂漠・氷原) で、洞窟の中身は共通。
   - 追加案: ジャングル (つる・泥・毒)・沼・サンゴの海 (水の広い領域)・地下のキノコの森・クリスタルの洞窟・地獄 (底の溶岩の層に、燃える岩)・浮遊島 (空)。
   - 各バイオームに、固有の材質 (背景の壁・植物・鉱石)・固有の敵 (§4.5)・固有の BGM (§4.9) を持たせる。
2. **木・草・花・岩 (推奨)**: 地表に木がない (家はある)。木は、木材 (クラフトの主材料) の供給源として**必須**に近い。今は木材を集める手段がない (木のセルは材質としてあるが、世界に生えない)。
   - 提案: 森のバイオームの表面に、幹 (木の固体セル) と葉 (葉の材質) を、決定的に生やす。木を斧で切る (つるはしと別の道具)、あるいは木のセルを掘る (今の掘る道具) で木材が得られる。
3. **地形の「滑らかさ」(推奨)**: 実機のスクリーンショットで、砂漠が急な崖、土の層が薄く、見た目が荒い。
   - 提案: 表面の高さのノイズに、より高い周波数の小さな丘を足す。バイオームの境目で、高さと材質を補間する。土の層を、洞窟の上でも厚く保つ (洞窟が表面近くを通ると崖になる)。
4. **洞窟の質 (推奨)**: 大広間・坑道・立て坑は、整数ノイズでつながるが、通路の幅が一様で、「空間の面白さ」(広間・吊り橋・滝・地底湖・縦穴の連続) が弱い。
   - 提案: 構造物 (§4.2.5) と、洞窟の中のミニバイオーム (地底湖・クモの巣・氷の洞窟)。
5. **構造物のテンプレートの拡充 (推奨)**: 今は、ダンジョン 3 種と家 1 種 (ブロックの文字の絵)。
   - 提案: 文字の絵を外部ファイル (RON またはテキスト) に出して、MOD で追加できるようにする。宝箱・扉・罠・松明・看板を置ける (§4.3 の機能ブロックが前提)。テンプレートの向き (反転)・バリエーション。
6. **鉱石と資源の流れ (必須)**: 石炭・鉄・金の 3 種。**使い道がない** (レシピは木と石だけ)。
   - 提案: 鉄・金の道具と防具、石炭の燃料と松明。ティア (木 → 石 → 鉄 → 金 → さらに深い鉱石) の進行表を作り、深さと敵の強さに対応させる。
7. **世界の seed とバランス検証 (推奨)**: 100 個の seed で、出発点の安全性 (表面が平ら、近くに立て坑)、鉱石の量、構造物の数を検証する自動テストを足す。今のテストは 1〜4 個の seed。
8. **水・溶岩の溜まりの危険 (推奨)**: 立て坑の底に溶岩の湖があるなどの危険を、検出して調整する。出発点の近くの洞窟が、溶岩に直結しないかを確認。

### 4.3 建築・ブロック・機能ブロック

1. **機能ブロック (必須)**: 作業台 (近くのレシピ)・かまど (精錬)・金床・箱 (収納)・ドア・看板・ベッド (リスポーン位置)・松明。
   - 現状: `recipes.ron` の `station` と `nearby_blocks` で「近くにそのブロックがあるか」は判定できるが、**そのブロックを作る・置く手段**は、石のブロックと木のブロックのみ (材質のブロック)。「作業台」というアイテムはない。
   - 提案: ブロックに「種類」(`BlockKind`: Plain / Station(名前) / Container / Door / Torch / Sign / Bed) を持たせる。ブロックは 8×8 の材質の塊だが、機能ブロックは「材質 + 種類 + 追加データ (箱の中身・看板の文字)」。保存は、ブロックの位置から追加データへの表をチャンクの隣に持つ。
   - 難所: 機能ブロックが壊れたとき (箱の中身の落下)、粉のブロックが崩れたとき (旗が外れる)、ブロックの押し出し (機能ブロックを押し出さない) との整合。
2. **ブロックの形 (推奨)**: 今は 8×8 の完全な正方形のみ。階段・斜面・半ブロック・板 (プラットフォーム、下から通り抜けられる) がない。2×3 ブロックの体が、1 ブロックの段差を自動で乗り越える設計なので、階段 (斜面) は快適さに直結する。
   - 提案: 形の種類 (`Shape`: Full / Half / Slope(向き) / Platform) を、機能ブロックと同じ仕組みで持つ。セルの旗 `FLAG_BLOCK` は 1 ビットで、これ以上は使えない (旗は 8 ビット中 8 つ使用)。形のデータは、チャンクの隣の表に持つ (§4.3.1 と共通)。
3. **ブロックの撤去の速度と道具 (推奨)**: つるはしの `pick` 値は定義だけで、**壊す速さに使っていない** (即座に壊れる)。硬さ (材質の `hardness`) と道具の力で、壊す時間 (進捗バー) を決める。
4. **ブロックの重さ・支え (任意)**: 空中にブロックを置ける (支えなくても浮く)。Terraria と同じで、これで良い。崩壊は、粉のブロックだけ。
5. **ブロックの建築の補助 (推奨)**: 長押しでの連続設置・ドラッグでの範囲設置 (線・矩形)・スマートカーソルでの「隣に置く」。タッチで家を建てるときの手間を減らす。実機で必要。
6. **元に戻す・設計図 (任意)**: 建築の「取り消し」、範囲のコピー (サンドボックスには Clipboard パネルがある) を、製品のモードにも。
7. **液体と建築 (推奨)**: ブロックを水の中に置く、液体を入れる容器 (バケツ)・ポンプ・パイプ。Terraria 型の仕掛け (水の流れで動くものなど) は大きな楽しさになる。
8. **ブロックの通信 (T19.5、必須 if マルチ)**: 置く・壊すを、`TickInput` のコマンドにする (プロトコルの版 4 → 5)。

### 4.4 アイテム・クラフト・経済

1. **アイテムの種類 (必須)**: 道具 (つるはし)・武器 3 種・防具 4 枠・消耗品 (体力・マナの回復) のみ。
   - 追加: 斧 (木)・ハンマー (壁)・ツルハシの階層・釣り竿・バケツ・弾薬 (矢・玉)・投げもの (爆弾・ナイフ)・翼 (浮遊の装備、今はプレイヤーに固定)・指輪の能力 (二段ジャンプ・水中呼吸・溶岩の耐性)・ペット・ミニオン (召喚)。
2. **アイテムの属性 (推奨)**: レア度・説明文・耐久・修飾 (「鋭い」「重い」)・スタックの上限 (種類ごと、今は一律 99,999)。
3. **ツールチップ (必須)**: 持ち物のアイテムにカーソルを合わせると、名前・説明・数値 (ダメージ・防御)・レシピの材料が出る。今は名前の先頭 6 文字だけ。
4. **アイコン (必須)**: 今は色付きの四角。自作のアイコン (16×16 程度) が要る。`items.ron` に `icon` を持たせ、アトラスから描く。素材は自作 (仕様 18 の方針: 他社の絵は使わない)。
5. **クラフトの画面 (必須)**: 今は egui の一覧と `Craft` ボタン。Terraria 型の「近くの作業台で作れるものを、材料のある順に並べ、選んで 1 回押す」体験に。絞り込み (`Filter: All`、仕様 18 の画像にある)・検索・お気に入り・材料が足りないものを薄く表示・作れる最大数。
6. **ドロップの一般化 (必須)**: `Drops` は材質のセルだけ。敵の戦利品に「ポーション」「装備」を入れるには、`Drop` を `ItemId` にし、`Pickup` の形を変える (**壊れる変更**。`Pickup { who, material, count }` を使っているテストと MOD が多いので、`item: ItemId` を足し、`material` は互換のために残す案が現実的)。
7. **店・通貨・価格 (推奨)**: NPC の店 (§4.5)。通貨アイテム (コイン)。売る・買う画面。
8. **箱・収納 (必須、§4.3 に依存)**: 箱の中のアイテムの保存・取り出し・クイックスタック (持ち物から箱へ同じ種類を送る)。
9. **ホットバーの運用 (推奨)**: ホットバーの選択はあるが、**ドラッグでの並べ替え**・ホットバー内のスワップ・数字キーとの対応の表示が不十分。タッチでは長押しでの移動。
10. **アイテムの落とす・捨てる・投げる (推奨)**: `drop_item` の API はあるが、UI から呼べない。

### 4.5 敵・AI・ボス・NPC

**現状**: `walker`・`shooter`・`skeleton`・`archer`・`mage`・`golem` (ボス)。歩いて、見えたら近づく (または距離をとる)、跳ぶのは「壁にぶつかる」か「目標が真上」のとき。

1. **経路探索 (必須)**: 壁・穴・段差で止まる。洞窟で、上下に離れたプレイヤーを追えない。
   - 提案: セルの格子を、体の大きさに合わせた「歩ける位置のグラフ」(ブロックの格子に落とした 2×3 ブロックの体の入る空き) にして、A* で数十ステップ先まで探索する。決定的でなければならないので、`BTreeMap` と固定の順序。計算量は、敵ごとに 5〜10 tick に 1 回、探索の上限 (ノード数 200) で制限する。
   - 近道: 「プレイヤーへの勾配 (距離の場)」を、プレイヤーのまわりの 100×100 セルで BFS して作り、敵は場を下る。敵が多いとき、1 つの場を共有できる (性能が良い)。
2. **敵の種類 (必須)**: 各バイオーム・深さに 5〜10 種。飛ぶ敵 (コウモリ・幽霊・鳥、重力なし・壁をすり抜ける/すり抜けない)、水中の敵 (魚・クラゲ)、穴を掘る敵 (ミミズ)、跳ねる敵 (スライム、現状は `walker` が跳ぶ)、飛び道具を避ける敵、群れ (集団で出る)、自爆する敵、分裂する敵、召喚する敵、透明な敵、地面を這う敵 (壁・天井を歩く)。
   - 敵の AI を、データ (`behavior: Walker | Flyer | Swimmer | Burrower | Jumper`) で選べるようにする。今は `step_enemies` の中に直書き。
3. **敵の見た目 (必須)**: `enemy_sprites` はデモの 2 種だけ。新しい 4 種は単色の箱。スプライトシート (歩く・攻撃・死ぬ)・向き・ダメージの点滅・死の演出。
4. **ボスの行動 (必須)**: ゴーレムは、体力 600 で、拳で殴り、接触でダメージ。専用の行動 (突進・衝撃波・弾幕・手下の召喚・段階 (体力 50% で変化))、アリーナ (ボスを呼ぶ祭壇・ボス戦中は帰れない境界)、ボスごとの専用の BGM・体力バー・倒したときの演出と報酬 (専用アイテム・次の層の解放)、複数のボスの順序 (進行)。
5. **スポーンの設計 (推奨)**: 今の規則は、y の範囲と重みだけ。追加: バイオーム別・時間帯別 (夜)・イベント (襲撃)・プレイヤーの強さ (防御の合計・ボスの撃破数) に応じた段階・安全地帯 (家の中・明るい場所では出ない: Terraria は「壁のある部屋」と「NPC のいる住居」では出にくい)・出現の演出 (地面から)・スポーンの位置の検証 (視線が通らない場所を選ぶ: 今は距離だけ)。
6. **戦闘の手応え (必須)**: ダメージの数値表示、ヒットストップ (数フレームの停止)、敵のダメージ点滅、ノックバックの耐性 (ボスは弾かれにくい)、無敵時間 (被弾後の数 tick: 今は 30 tick 周期の接触ダメージのみで、弾・近接の連続ヒットに無敵がない)、攻撃の予告 (敵の攻撃の前の合図)。
7. **NPC (推奨)**: 村人・商人・看護師。住居 (壁と部屋の判定)・昼夜での行動・会話・店。住居の判定 (密閉された部屋・家具) は、機能ブロック (§4.3) とセットで、実装が大きい。
8. **ペット・ミニオン・味方 (任意)**。
9. **敵の同期 (マルチ) (推奨)**: 敵の状態をホストだけが決め、クライアントへ送る方式か、全員が同じ入力で決定的に進める (Lockstep) か。今の設計は Lockstep なので、乱数・順序の決定性は保たれているが、スポーンの `rng::hash(seed, tick, ...)` は全員が同じ値になる。**プレイヤーの数が変わる (途中参加)** と、再同期が難しい。
10. **敵の落下ダメージ・環境ダメージ (推奨)**: プレイヤーにも落下ダメージがない (高所から落ちても無傷)。Terraria 型では必要。

### 4.6 プレイヤー・移動・探索

1. **落下ダメージ (推奨)**: 高さによるダメージ。装備で無効にできる。
2. **泳ぎ (必須)**: 水の中での移動 (浮力・泳ぐ・水中の速度)。今は液体のセルが体と重なっても、移動の規則は同じ (息が減るだけ)。水の中を歩いて、ジャンプで泳ぎ上がれない。
3. **はしご・ロープ・登る (推奨)**: 壁を登る手段。フックはあるが、はしごがない。
4. **しゃがむ・降りる (推奨)**: 左スティックの下に「足場から降りる」(仕様 18) があるが、足場 (プラットフォーム) がない (§4.3.2)。
5. **ダッシュ・二段ジャンプ・グライダー (任意、装備で)**。
6. **乗り物・マウント (任意)**: 馬・カート・飛行。
7. **見た目のカスタマイズ・装備の見た目 (推奨)**: 装備を付けても、プレイヤーの見た目が変わらない。スプライトのレイヤー (体・頭・胴・脚・武器)。仕様 15 のスプライトの仕組みをレイヤーに拡張。
8. **アニメーション (必須)**: 歩く・跳ぶ・落ちる・掘る・振る・撃つ・死ぬ。`animation.rs` はある (歩く・止まる・跳ぶ程度)。武器を振る・つるはしを振るの腕のアニメーション。
9. **カメラ (推奨)**: 追従と揺れはある。先読み (進む向きを少し先に)、ボス戦のズーム、トランジション。

### 4.7 戦闘・魔法

1. **杖の拡張 (推奨)**: 呪文 5 つ。Noita 型の「呪文の組み合わせ (修飾・トリガー)」は仕様 10 §5 にあるが、デモ用の杖は単純。ツリー (呪文をつなぐ)・ドロップ (敵から杖を拾う)・杖の強化。
2. **属性の拡張 (推奨)**: 火・毒・冷気の耐性はあるが、冷気 (凍結・水が氷になる) の「攻撃側」の仕組みがない (冷気の呪文・凍る状態)。雷 (水に伝わる)・酸・魔力。
3. **状態異常の拡張 (推奨)**: 凍結・感電・出血・スロー・弱体・強化。ポーションでの強化 (一時的な能力の上昇)。
4. **武器の個性 (必須)**: 近接はスイングの弧 (いまは前の箱)・突き・薙ぎ払い・飛ぶ斬撃。遠距離は弾種 (矢の種類)・連射・溜め撃ち。投げもの。武器ごとのダメージの幅 (今は固定値)・クリティカル。
5. **防具のセット効果 (任意)**。
6. **ダメージの式の調整 (必須)**: 物理は `amount − defense` (元の 1/4 が下限)。防御が積み上がると、後半の敵に対して、防御の効きが急に変わる。Terraria は「防御の半分」を引く。式の選択は、バランス調整で決める。
7. **PvP (任意)**。
8. **敵の火の玉・魔法による環境の破壊 (推奨)**: 火の玉は周りを燃やす。爆発 (bomb) は地形を壊す (パーティクルになる)。プレイヤーの家 (木のブロック) が、敵の火の玉で燃え広がると、建築が壊れる。木のブロックの耐火・「火に強いブロック」の選択肢が要る。

### 4.10 保存・進行・設定

1. **プレイヤーの保存の配線 (必須)**: `GameSave::with_items` / `apply_items` を、App の保存と復帰の経路 (`save_game`・`pending_game_save`) につなぐ。今は、セルの持ち物 (`inventory`) とブロック (`blocks`) は保存されるが、**定義のアイテム・ホットバー・装備は保存されない**。仕様 19 §7 にあるのに、App が呼んでいない。
2. **保存の版管理 (必須)**: `GAME_SAVE_VERSION = 1` のまま、項目を足している (`serde(default)`)。これは「足すだけ」の変更に限り安全。型の変更・削除には、移行 (`migrate_v1_to_v2`) の仕組みが要る。ワールドの保存 (`world.ron`、リージョン) にも、版と移行がある (仕様 04)。**M19〜M24 の材質の追加 (4 つ) は、末尾への追加で互換**。材質の順序・名前を変える変更は、保存を壊す。
3. **自動保存・保存のタイミング (必須)**: 今の保存のタイミング (終了時・メニューで?)。クラッシュ時の損失。一定間隔 (例えば 60 秒) と、重要な出来事 (ボスの撃破・就寝) での自動保存。保存の失敗の通知。
4. **複数のワールド・プレイヤー (推奨)**: ワールドの一覧・削除・複製。プレイヤー (キャラクター) をワールドと別に保存し、複数のワールドで使う (Terraria 方式)。
5. **クラウドセーブ・バックアップ (任意)**: 保存の破損に備えて、直前の版を 1〜2 個残す (`game.ron.bak`)。
6. **設定 (済み・一部)**: `settings.ron` (UI の大きさ・光・音量・キー・更新距離)。言語・画質のプリセット・操作の設定・アクセシビリティを足す。
7. **実績・統計 (任意)**: 「初めて木を壊した」など。ストア連携は別。
8. **進行 (必須)**: ボスの撃破・解放したレシピ・訪れたバイオームの記録。進行のフラグを保存。
9. **難易度・ハードコア (推奨)**: 死亡のペナルティ (アイテムを落とす・通貨を失う)・ハードコア (死んだらキャラクターを削除)。今の復活は、ペナルティなし。

### 4.11 マルチプレイ・通信

**現状**: `charon-game` に `net.rs` と `lockstep.rs` (入力の同期とハッシュの照合)・ホスト中継の TCP (標準ライブラリのみ)。アプリへは組み込んでいない。

1. **アプリへの組み込み (必須 if マルチ)**: ホストする・参加する画面、入力の収集と送信、遅延の吸収、切断の処理。
2. **コマンドの拡張 (T19.5)**: `TickInput` に、ブロックの置く・壊す・アイテムの使用・装備・クラフト・持ち物の操作を足す。プロトコルの版を 4 → 5。
3. **途中参加 (必須 if マルチ)**: Lockstep は「全員が最初から同じ状態」が前提。途中参加には、ホストが世界の状態を送る (チャンクの転送・全エンティティの状態) か、スナップショットからの再生が要る。ワールドが無限に近いので、「参加者の周りのチャンクを送る」方式にする。
4. **帯域と遅延 (推奨)**: 入力のみを送るので、帯域は小さい。ただし、**決定性が破れると破綻する** (ハッシュの照合で検出するが、復旧がない)。浮動小数点を使う剛体 (`charon-physics`) は、プラットフォーム間で結果がずれうる (仕様 13 の注意)。剛体は、ホストだけで計算し、結果を送る方式も検討。
5. **チート対策 (任意)**: Lockstep はクライアントが入力だけを送るので、改ざんの余地が小さい。ホスト中継の認証 (接続情報の照合はある)。
6. **ローカル協力 (任意)**: 1 台の画面で 2 人 (分割・共有画面)。

### 4.12 チュートリアル・進行の導入・ゲームデザイン

1. **最初の体験 (必須)**: 現在は、最初の 25 秒のヒント行だけ。「木を切る → 作業台 → つるはし → 家 → 夜を越す → 洞窟 → ボス」の目的の連鎖を、ガイド (NPC の助言・画面の目標の表示)・実績で示す。
2. **ゲームの目的 (必須)**: 何をすれば「進んだ」ことになるか (Terraria: 装備を強くしてボスを倒す)。今は、世界を歩いて、敵を倒せるだけ。
3. **難度曲線 (必須)**: 深さと敵の強さ・防具のティア・ボスの順序。仮の数値を、通しプレイで調整する。調整用の数値を 1 か所 (`balance.ron`) にまとめ、再起動なしで読み込み直せる (開発ビルド) ようにする。
4. **リスクと報酬 (推奨)**: 危険な場所 (溶岩・ダンジョン) の見返り (宝箱・レアな鉱石)。
5. **復活の位置 (推奨)**: ベッドで復活 (§4.3.1)。今は出発点のみ。
6. **ゲームのモード (任意)**: クリエイティブ (無限のブロック・飛行)・サバイバル・ハードコア。**サンドボックスのモード (今の Draw / Clipboard など) は、クリエイティブとして製品に残せる**。

## 5. 既知の簡略化・不具合・懸念 (M19〜M27 の実装の記録)

「実装中に、分かっていて残したもの」を、隠さずに挙げる。

### 5.1 操作・UI

1. 体力・マナは、仕様 18 のハート・星ではなく、小さなバー。
2. ホットバーの見える枠は 5 つ + `...` (タッチ)。デスクトップは 10 枠、数字キー。
3. 装備した武器をホットバーで選ぶと、**持ち物から装備に移る** (持ち物の個数は 0 になり、ホットバーは「装備中」として表示を続ける)。武器の入れ替えは、別の武器を選ぶと、元の武器が持ち物に戻る。持ち物が満杯のときの扱いは `NoRoom` で失敗するのみ (UI の通知なし)。
4. フックは、投げたら張りっぱなしで**自動で巻き取る** (Terraria 型)。振り子のように揺れるだけの操作はできない (仕様 18 §2.1 の「要確認」)。
5. スマートカーソルの探索は、向きの直線上の最初の固体 (仕様 18 §5 の案)。
6. 画面のなぞりでカーソルを動かす方式は作っていない (仕様どおり)。タッチの部品の外の 1 本指は何も動かさない。
7. 数字キー・左ボタンは、UI (egui) がイベントを使っていると無視される。
8. デモの開発用パネル (`Draw`・`Clipboard` 等) が、製品の画面に残っている (§4.8.3)。デスクトップの最初のパネルが、ホットバーと重なる問題は、ホットバーを下の中央に移して回避した。
9. 持ち物の画面の文字は英語。ツールチップなし。

### 5.2 戦闘

1. ダメージの数値・確率は、すべて仮。
2. 近接は「前の箱」で、スイングの弧・ヒットの順序・多段ヒットの制御がない (1 回の攻撃で、箱の中の全員に 1 回)。
3. 物理の被ダメージの下限は元の 1/4。
4. 無敵時間がない (接触ダメージの 30 tick の間隔だけ)。弾・近接の連続ヒットで、短時間に大きく削られる可能性。
5. ノックバックは、弾・近接の向き。爆発のノックバックはない (ダメージのみ)。
6. 敵の近接 AI: 目標が箱に入ったら斬る。攻撃の予告・前進しながらの攻撃はない。同士討ちなし (敵同士は当たらない)。
7. 火の玉の発火は、半径 4 の円の市松に火を置く。燃え広がりは、通常の規則 (木・油が燃える)。**プレイヤーの木のブロックの家は燃える**。
8. 矢は弾薬を消費しない。

### 5.3 世界

1. 砂漠の表面が急な崖になる場面がある (スクリーンショットで確認)。
2. 土の層は 22〜29 セルで、洞窟が表面近くを通ると、層が途切れる。
3. 背景の壁・光源・植物がないので、世界が単調。
4. 立て坑は、x = 160〜319 の区画に必ず 1 本 (出発点の近く)。ほかは 1/3 の確率。深さ 100 までなので、洞窟と交わらない立て坑は、行き止まり。
5. 池は、森と氷原にのみ。氷原の池は凍らない。
6. 出発点は、x = ±24 が平ら。それ以外は丘。
7. 鉱石の使い道がない (§4.2.6)。
8. 底の溶岩の湖は、底の手前 24 セル。落下した先が溶岩 (即死に近い) になりうる。
9. `AdventureGenerator` は、`DemoConfig::adventure` が既定で真。古いデモの世界 (`CHARON_WORLD=demo`) は残している。
10. 世界を新規に作ると、デモの `Random Seed` は `adventure-<seed>` の保存先 (`saves/demo/adventure-N`)。

### 5.4 範囲の外の移動 (M27)

1. 液体は落下のみ (広がらない)。気体は上昇のみ。
2. 4 tick ごと・最大 8 セルなので、**落下の速度は、通常の更新より遅い** (通常は、水は 1 tick に 1 セル以上動くが、範囲の外は 2 セル / tick 程度)。範囲に入ると、通常の速さに戻る。
3. 範囲の外の全セルを走査する (§7 の施策 2)。
4. 液体の「境界」(範囲の内側と外側の境目) で、内側の通常の更新と外側の粗い更新が、同じ列で交互に動くことがある。
5. 液体に重なる低密度・高密度の入れ替え (水の上の油など) は、粗い移動では行わない。

### 5.5 敵・スポーン

1. `Spawner` の候補位置は `walker` の大きさ (16×24) を前提 (すべての敵が同じ大きさ)。
2. 視線を見ない。画面の外にも、同じ高さの穴の中にも出る。
3. ボスは、深さ 700 以上で、12 回の試行に 1 回、同時に 1 体。ボスから逃げる・ボスを呼ばない選択がない (ランダムに出る)。
4. 戦利品は材質のセルのみ。`block:`・定義のアイテムは出ない。
5. 敵のスプライトは、`walker`・`shooter` のみ。

### 5.5b 保存

1. §4.10.1。装備・ホットバーが保存されない。
2. 敵・弾・ドロップは保存しない (読み込み後に再び生まれる)。

### 5.6 コード上の懸念

1. `GameState` のフィールドが増え続けている (equipment・weapon_cooldown・spawner・death_timer・item_defs など)。`pub(crate)` で兄弟のモジュールから触っている。サブシステムごとの構造体に分ける。
2. `Hit` の項目追加・`Pickup` の形・`SoundBank` の項目は、構造体の直接構築を壊す。
3. `ProjectileWorld::spawn` が 9 引数 (clippy の許可つき)。
4. `charon-app` の `lib.rs` が約 2,000 行。
5. テストの座標の直書き (M21 で大量に書き換えた)。
6. `demo_ui.rs`・`demo_render.rs` が 1,500 行級。

## 6. 品質・保守性の改善

### 6.1 設計

1. **サブシステムの分離**: `GameState` を、`Combat`・`Loadouts`(持ち物・装備・ホットバー)・`Spawning`・`Lifecycle`(死亡・復活) に分け、`step` は順序を決める薄い指揮者にする。各サブシステムが、自分のテーブル (`BTreeMap<EntityId, …>`) と状態のハッシュを持つ。
2. **イベントの設計**: `GameEvent` は `non_exhaustive` で追加に強い。ただし、種類が増える (現在 12 以上)。サブシステム別のイベント (`CombatEvent`・`BuildEvent`) にして、音・演出・スクリプトが、必要な種類だけ購読する。
3. **入力の設計**: `GameInput { fire, tool, dig, aim }` は、Lockstep のプロトコルに直結。M22 の操作 (使う・フックの投げる・ホットバーの選択・カーソル) の多くは、**App の局所の処理** (`build_input`) で、ゲームの状態を直接変えている (`use_selected`・`equip`)。マルチでは、これらを**コマンド**として Lockstep に載せる必要がある。今のうちに、`Command` の列挙 (`Use { cursor }`・`Select(slot)`・`Craft(name)`・`Equip(item)`・`Hook(dir)`) を `charon-game` に定義し、App はコマンドを発行するだけにする。これは、リプレイ (§4.13.7) と、マルチ (§4.11.2) の両方の土台になる。
4. **データ駆動の徹底**: `Spawner::adventure()`・テンプレート (`HALL`/`TOWER`/`CRYPT`/`HOUSE`)・バランスの数値 (`MELEE_REACH`・`KNOCKBACK_BASE` 等) が、Rust のコードにある。RON に出して、MOD とバランス調整を、再コンパイルなしにする。
5. **敵の AI の設計**: 直書きの `step_enemies` を、振る舞い (`Behavior`) のトレイトまたは列挙にして、データで選べるようにする (§4.5.2)。
6. **エンティティの設計**: エンティティは、箱 + 速度 + 旗。種類 (プレイヤー・敵・アイテム・弾) が、複数のテーブルに散らばる。ECS (自前の軽いもの) への移行は、性能と拡張に有利だが、決定性 (反復順) に注意。大きな変更なので、必要が出てから。

### 6.2 コード品質

1. 構造体の初期化のビルダー化・`Default` の整備 (§5.6.2)。
2. 引数が多い関数を、構造体の引数に (`SpawnParams`・`BlockPlaceParams`)。
3. 長い関数の分割 (`step_enemies`・`GameState::step`・`App::redraw`)。
4. `unwrap`/`expect` は、テスト以外で使わない (規則どおり)。`build_input.rs` のテストの補助で `panic!` を使った箇所は、テストの `unwrap` に統一。
5. コメントの言語: 日本語で統一 (現状どおり)。公開 API の `rustdoc` に例を足す。
6. `cargo doc` の警告ゼロ (今は通っている)。
7. 依存クレートの更新方針 (`cargo update` の定期実行・`cargo audit`)。

### 6.3 テスト

1. **座標の直書きの整理**: `testkit` に「床の上に N×M の体を立たせる」「幅 W の部屋を作る」「ブロックを置く」の補助を足し、テストが体の大きさ (`PLAYER_WIDTH`・`PLAYER_HEIGHT`) を参照して座標を決める。
2. **プロパティテスト**: ブロックの置く・押し出す (セルの数が増減しない・全部か何もない)、保存の往復 (任意の状態)、スポナー (上限・距離)、粗い流れ (保存則)。`proptest` を、決定的な seed で。
3. **ゴールデンテスト**: 地形生成のハッシュ (seed 1〜10 の特定のチャンクのハッシュ) を、固定値で持つ。生成の意図しない変更を検出する (変更したら更新を明示する)。
4. **ミュータント**: 重要な規則 (ダメージ・段差・復活) を、わざと壊したときにテストが落ちることの確認 (`cargo-mutants`)。
5. **描画テストの安定化**: GPU のない CI では描画テストが飛ぶ。ソフトウェアのラスタライザ (lavapipe 等) を CI に入れる検討。
6. **統合テスト**: 「起動 → 歩く → 木を集める → 作る → 置く → 敵を倒す → 保存 → 復帰」を、ヘッドレスで自動の入力で通すシナリオ (`charon-app` のヘッドレス)。

### 6.4 文書

1. ROADMAP・STATUS・GAME_API・PLATFORM_CHECK・BENCHMARKS・ENGINE_CHECKLIST を、M27 の状態に合わせる。

## 7. 性能

### 7.1 現状の数値

| 指標 | 値 | 出典・条件 |
|---|---|---|
| 100 万セル (砂 + 空行) を 1 tick 更新 | 約 35〜41 ms | `docs/BENCHMARKS.md`、目標 8 ms は未達 |
| 溶岩の池 (60×9) | 煙が消えても毎 tick 約 1,500 セル | 熱の更新が眠らない |
| 冒険の世界の生成 | 165 チャンクで約 0.8 秒、1 チャンク約 5 ms | 開発用の最適化つきビルド (`opt-level = 1`)、Ryzen 7 2700 |
| デモの 1 フレーム (描画 + 更新) | 約 2〜3 ms (469 FPS) | GPU の描画テスト (小さな場面) |

### 7.2 「目標 8 ms / 100 万セル」の再定義

100 万セルを毎 tick 動かす場面は、商品では起こりにくい。実際に更新されるのは、**画面のまわりで、休眠していないセル**だけ。商品の予算として、次の 3 つに分けて、目標を作り直す。

- **予算 A (デスクトップ、60 FPS)**: 1 フレーム 16.6 ms のうち、シミュレーション 6 ms・描画 5 ms・ゲーム 3 ms・余裕 2.6 ms。
- **予算 B (Android の中堅機)**: 同 16.6 ms (60 FPS) または 33 ms (30 FPS)。シミュレーション 8 ms (30 FPS のとき)。
- **場面**: 「地表を歩く (水・砂が少し動く)」「洞窟で戦う (溶岩・火・爆発)」「大規模な水の落下 (池が崩れる)」「100 体の敵」「ボス戦」の 5 場面で、tick 時間の p50・p95・p99 を記録する。

### 7.3 計測の整備 (施策の前提)

1. **フレーム内の分解**: シミュレーション (フェーズ別)・剛体・ゲーム・生成・保存・描画 (パス別)・UI。`tracing` クレートの `span` (開発用の feature) と、Tracy / Chrome の trace 形式での出力。
2. **カウンタ**: 更新したセル数・更新したチャンク数・休眠のチャンク数・エンティティ数・弾の数・ドロップの数・読み込みチャンク数・メモリ。
3. **場面の自動実行**: 冒険の世界に、決まった入力 (ボット) で入り、5 場面を再現して、数値を JSON で出力する (CI の記録)。
4. **メモリの計測**: ピークと増加の傾き (ソークテスト)。

### 7.4 施策 (効果の大きい順、実装の難しさつき)

**S1. 溶岩の熱を眠らせる** (効果: 大 / 難しさ: 中 / 結果が変わる)
- 問題: 熱の伝導は、隣との温度差がある限り更新が続く。溶岩 (1400°) と石 (20°) の境目は、定常に近づいても、整数の丸めで、`±1` を行き来しうる。溶岩のセル自身は、`keep_awake` で目覚め続ける。
- 案 1: 「温度差が `Δ_min` (例えば 2) 未満なら書き込まない」しきい値。丸めの振動が止まり、休眠できる。
- 案 2: 溶岩の `initial_temp` を一定に保つ「熱源」として扱い、熱源と同じ温度のセルは、周りが熱源の温度に近いとき眠る。
- 影響: シミュレーションの結果が変わる (仕様 03 の更新)。決定性は保たれる。ベンチの比較・テストの更新が要る。**持ち主の承認が必要**。
- 期待: 深い洞窟・溶岩の湖で、毎 tick の更新セル数が 1/10 以下。

**S2. 範囲の外の粗い流れの走査の削減** (効果: 中 / 難しさ: 小 / 結果は変わらない)
- 問題: M27 は、範囲の外の全チャンクの全セル (4,096) を、4 tick ごとに走査する。範囲の外の読み込み済みチャンクが 200 個なら、毎 tick 約 20 万セルの走査。
- 案: `Chunk` に「液体・気体のセルの数」(`fluid_count`) を持たせ、`set` で更新する。0 のチャンクは走査しない。さらに、「最後に動いたか」(`coarse_settled`) を持ち、液体がすべて固体・境界の上にあるチャンクは、次に周りが変わるまで、走査しない。
- 期待: ほとんどのチャンクで走査が 0。

**S3. 地形生成の並列化・先読み** (効果: 中〜大 (Android) / 難しさ: 中)
- 生成は純粋関数 (`ChunkGenerator::generate`) なので、ワーカースレッドで並列に作れる。`Streamer` が、進行方向 (プレイヤーの速度) のチャンクを先に要求し、結果をチャンネルで受け取る。ただし、**`charon-core` はスレッドを作らない**規則 (CLAUDE.md) なので、`charon-world` の側で行い、`std::thread` を使うか、`rayon` (`parallel` feature) を使う。
- Android での、チャンクの読み込みのカクつきの対策として重要。

**S4. 洞窟ノイズの計算量の削減** (効果: 中 / 難しさ: 小〜中 / 結果が変わる)
- 現在、1 セルあたり、洞窟の判定でノイズを 6 回前後評価する (歪みに 2・広間に 2・坑道に 2・粗さ 1)。
- 案: (a) 表面の層 (深さ < 26) と、構造物の内側では洞窟の判定を飛ばす (済み: 深さで)。(b) ノイズの格子を、4×4 セルごとに評価して補間する (結果が変わる)。(c) 列ごとに、洞窟のない深さの範囲を前計算する。(d) SIMD (安定版の `std::simd` はまだ。自動ベクトル化を助ける形に)。
- 期待: 生成時間が 1/3〜1/2。

**S5. 描画の最適化** (効果: 中 / 難しさ: 中)
- 光 (xHigh) の計算を、解像度を下げて行い、アップサンプルする。Android の既定を Low に。
- チャンクのテクスチャの更新を、変わったチャンクだけ (済み?: dirty の使用を確認)。
- スプライト・剛体の描画は軽い。UI (egui) のメッシュの生成が、パネルが多いと重い (開発用パネルを隠せば減る)。
- バッテリー・熱: 60 FPS の固定ではなく、画面が静止しているとき (ポーズ・メニュー) は描画を間引く。

**S6. 並列度の調整** (効果: 小〜中 / 難しさ: 小)
- 9 フェーズ並列は、同じフェーズのチャンクが少ないと効果が薄い。更新するチャンクが少ない (10 未満) とき、直列にする。`rayon` のスレッド数の上限 (Android の big.LITTLE での調整)。

**S7. エンティティ・敵の処理** (効果: 小〜中 / 難しさ: 小〜中)
- `collides` (楕円と格子の判定) が、エンティティごとに多数呼ばれる。段差の乗り越え (`obstacle_height`・`step_lift`) は、最大 8 セル × 数回。敵 100 体で、1 tick に数万回。
- 案: 遠い敵 (プレイヤーから離れたもの) は、AI を間引く (5 tick に 1 回)・物理は、コールドフリーズの外では止める (今も止まる?: スポーナーが削除する)。経路探索 (§4.5.1) は、予算を決める。

**S8. メモリ・割り当て** (効果: 小 / 難しさ: 小)
- 1 tick 内の `Vec` の生成 (`step_enemies` の `ids`・`step_spawner` の `players`・`coarse_flow` の `outside`・`Definitions` の clone (`GameState::step_spawner` を呼ぶ App が、毎 tick `defs.clone()`? いいえ、App は参照で渡す。テストの補助は clone))。再利用するバッファ (`SmallVec`・フィールドに持つ `Vec` を `clear`) に。
- `GameState::from_definitions` が `item_defs` をクローンする (1 回のみ)。

**S9. 保存の非同期化** (効果: 中 (カクつき) / 難しさ: 中)
- リージョンの書き込み (LZ4 の圧縮 + ファイル I/O) を、別スレッドで。保存の途中でクラッシュしても壊れないよう、一時ファイルに書いて置き換える (済み: `game.ron` は一時ファイル経由)。ワールドのリージョンも同様か確認。

**S10. 起動時間・読み込み** (効果: 中 / 難しさ: 小)
- `ModPack::load` と `Definitions` の構築、`include_str!` の RON の解析。起動時の 1 回。アセット (画像・音) の読み込みを遅延・並列に。

**S11. ワールドの広さに対する長期の安定** (効果: 必須 / 難しさ: 小)
- ソークテストで、メモリ (読み込みチャンクの解放・ドロップ・弾・敵の上限)・tick 時間の増加を確認する。上限 (`MAX_DROPS = 256`・`MAX_PROJECTILES`・`MAX_ENEMIES` の同時数) は、定義の範囲にある。

### 7.5 性能の回帰を防ぐ仕組み

1. `docs/BENCHMARKS.md` の場面を、CI で実行し、tick 時間の中央値が基準の +20% を超えたら失敗 (CI の機械のばらつきがあるので、相対値と複数回の実行で)。
2. 決定的な「更新したセル数」(機械に依存しない) を、回帰の主な指標にする (時間ではなく、仕事の量)。
3. 変更の前後で、場面ごとの更新セル数・チャンク数を、PR の説明に自動で出す。

## 8. リスクと判断が必要なこと

1. **実機で「遊べない」ことが分かるリスク (最大)**: 体の大きさ・移動・タッチの操作は、数値を決めただけ。実機で「重い」「大きすぎる」「操作しにくい」となると、M21・M22 の数値の見直し (テストの座標は定数経由なので、定数の変更で追従できるものが多い) が要る。早めに確かめる。
2. **性能の目標を満たせないリスク**: §7.2 の再定義と、S1 (熱の休眠) の承認が必要。
3. **決定性の破れ (マルチ)**: 浮動小数点の剛体 (rapier) は、プラットフォームで結果がずれうる。マルチを出すなら、剛体をホストの権威にする、または剛体を使うゲーム機能を限る。
4. **保存の互換**: 開発中の保存が、次の版で読めなくなる。製品版では、移行の仕組みを先に作る (§4.10.2)。
5. **範囲の拡大 (スコープクリープ)**: 本報告の項目は、数年分。商品として何を v0.1 (最小の商品) に入れるかを決める必要がある (§9)。
6. **法務**: Terraria との類似 (操作・世界の構造・敵の種類)。名称・絵・音・文字は使わない。ゲームデザインの「仕組み」の類似は、一般に保護されないが、判断は専門家に。
7. **アセットの制作**: 絵・音・BGM・フォントは、制作の時間と費用がかかる。自作・生成・フリー素材 (ライセンス確認) の方針を決める。
8. **一人開発の継続**: 自動テストと仕様が、品質を支えている。仕様の更新を怠ると、ずれが溜まる (§6.4)。
9. **判断が必要な 3 つ**: (a) 溶岩の熱の休眠 (結果が変わる)、(b) 商品の範囲 (v0.1 に何を入れるか)、(c) マルチを出すか (出さないなら、§4.11 を丸ごと後回しにできる)。

### 10.2 用語

- **セル**: 格子の 1 マス (1 ピクセル)。**チャンク**: 64×64 セル。**ブロック**: 8×8 セルの塊 (`FLAG_BLOCK`)。
- **休眠**: 変化のない領域を処理しない仕組み。**コールドフリーズ**: カメラから遠いチャンクの更新を止める仕組み (更新距離)。**粗い流れ** (`coarse_flow`): コールドフリーズ中の液体の落下・気体の上昇。
- **Lockstep**: 全員が同じ入力で、同じ状態を計算する同期方式。
- **ティア**: 装備・資源の段階。
