# E05：圧力・物性・scalar・正規粒子を一取引へ連結するMaterials phase

## 公開APIと実行順

WorldEdit::step_material_phase(config, provider) はWorldの正規候補へE05の個別処理を一度だけ結合する。MaterialPhaseConfigでは圧力緩和、cellのQ16力積分とDDA輸送、標準scalar移動、正規物質粒子の力積分とDDAを個別に有効化できる。

順序は pressure → cell force+DDA → scalar → canonical particle force+DDA。Noneなら該当処理を完全省略する。pressureは圧力場の緩和であり、source/sinkを生まない。すべての処理は既存の候補制限、整数演算、未読込の延期、予約、エラー診断を維持し、成功報告をMaterialPhaseReportとして返す。

### 連続するcell処理の共通予約

独立レビューでは、当初の力学DDAとscalarを続けて呼ぶ実装が、同tickで砂をDDAにより下へ1cell動かした後、scalarでさらに下へ1cell動かせることが判明した。両solverの単独APIはそれぞれ内部で予約を初期化するため、単純に直列呼出ししても「同じトークンをそのphaseで一度だけ動かす」という設計要件を満たさない。

統合Materials phaseでは、両処理へ同一のCellReservationsを渡す。DDAで使った始点・着点・通過点と角の検査点をscalarが再利用できない。単独APIは従来通り新規予約から開始して後方互換とし、統合モードだけがphase全体のトークン予約を提供する。このため、**両処理を同時に選んだ場合の結果は、予約を共有しない旧来の直列呼出しとは意図的に異なる**。異なる前提で得た結果を決定論的一致の参照と誤認しない。

またsimulated=falseのlayerは物質solverの対象外なので、phase入口とlayer指定の粒子力積分・DDA入口で拒否する。誤った指定により装飾など非物理layerの粒子が移動してしまうことを防ぎ、失敗時のcheckpoint不変を検証する。

独立レビューで、初回統合APIがtarget layerの指定をcanonical粒子処理に渡さず、別layerの粒子まで各phaseで更新してしまう不具合を発見した。これを防ぐため、従来のWorld全域粒子APIはそのまま残して、`integrate_material_particle_forces_in_layer`、`step_material_particle_forces_in_layer`、`step_material_particles_in_layer`を追加した。phaseは必ず指定layerだけを処理し、先行・後続layerの粒子の二重積分・着地をしない。他layerの粒子の開始位置は従来どおり占有として予約する。

同じ統合phaseではcell force+DDAとscalarを単独実行時とは異なり**共通の予約scratch**で扱い、同じトークンを一tick内に二度移動させない。さらに粒子DDAもこのscratchを読み、粒子の開始セル・通過セル・角の検査セルが先行するcell移動/scalarの予約と重なる場合は待機する。cell処理を含まないphaseでは、このscratchを確保しない。標準DDAとscalarの通行確認は、resident正規粒子の同layerにおける現在位置を所有済みとして扱い、見かけのAIRセルに自動移動して2つのトークンを重ねない。他layerの粒子や、作者が意図的に直接重ねたWorld状態は既存契約どおり保持する。未読込・非活動域は常に待機判定を優先し、粒子の存在を理由に確定衝突として速度を消さない。粒子単独APIは従来どおり独立実行であり、cell solverとの共有予約はMaterials phase経由に限る。

粒子側の追加費用は、最大DDA境界数`dda_steps`に比例する各境界・guard pointの予約bitset参照（chunk座標の二分探索とbit検査、最大3point/境界）で、候補数と境界数は既存のcandidate/step limitに従う。共有bitsetの追加確保や全World走査は行わず、粒子経路scratchは既存DDAと同じ経路長上限に従う。比較benchmarkは未実施であり、性能改善は主張しない。

### 広域移動Job・押出し探索との同tick共有

`WorldEdit::step_material_phase_with_jobs`はReady済みの`MaterialMotionJob`と`PressurePushSearch`を先に原子的に公開し、同じlayerの移動・押出し経路、source/destination、移動DDAの角確認点をMaterialPhaseの共通予約へ登録する。その後の通常cell DDA、scalar、正規粒子DDAはそのcellを再利用しない。Provider力積分も予約cellを対象外にし、Jobが既に移動した素材へ同tickの力を二重適用しない。PressurePushSearchは従来のpressure snapshotに基づき、後続の圧力緩和から探索を作り直さない。

Jobの全入力・経路予約を事前検証し、既存Job batch内の再検証を含む二回分の保守的な検証workを`job_cells`へ、batch scratchと共有reservation bitsetを合わせたbyte数を`job_bytes`へ収めてから確保する。Job公開後の標準phaseが失敗すれば、広域Jobも含めWorld候補全体をrollbackする。追加workはactive chunk照合とJob経路/node数に比例し、scratchはJob数・押出し経路長・active chunk数に比例する。固定容量を越えた場合は公開せず失敗する。比較benchmarkは未実施であり、性能改善は主張しない。

`WorldEdit::step_material_phase_with_pressure_jobs`はさらにReady済みPressureJob群を含める。圧力出力、移動/押出しJob、通常MaterialPhaseを指定順で一候補へ適用する。pressureと移動Jobの入力は公開前に元Worldで検査し、圧力出力scratchと広域移動batch・phase共有bitsetを合わせて`job_bytes`、二重に行う移動Job検証とPressureJob検証を合わせて`job_cells`へ収める。PressurePushSearchは元Worldのsnapshot経路を使うため、PressureJob出力後に新しい圧力から再探索する動作は含まない。後段の失敗は圧力出力・移動・押出しを含めてrollbackする。

独立レビューの追加指摘に従い、非simulated layerをparticleだけ指定しても移動させず、原子的なエラーとして拒否する。標準scalarとセルの整数DDAは、同layerのresident正規粒子の現在位置を一度だけ索引化し、未処理粒子の位置へtokenを侵入させない（別layerの粒子には干渉しない）。これらは既存solverの不足を修正するもので、phase APIの呼び出しだけに限定しない。元のWorld全域粒子APIは従来のlayer対象動作を維持する。

独自MaterialForceProviderを同じ力学入口へ渡せる。作者がProviderのキー・版と保存済み状態を管理し、隠れた標準重力を重複させない。Providerの外部IO・未保存の可変状態は本APIが保証する取引には含まれない。

## 原子的確定とRuntime

WorldEdit::runで既存各処理を包むため、先行の力積分・scalar輸送・粒子移動が成功しても後段の候補上限やchannel容量失敗でWorld::editが丸ごとrollbackする。個別処理は独自の成功reportを返し、必要な部分だけを診断できる。

作者は通常のWorld::edit、全表現台帳を保護するWorld::edit_material_accounted、またはRuntimeのWorldAccess::edit_material_accountedから、Materials barrierでこの統合処理を呼び出せる。region IOや永続保存を未確定World候補の内部で実行しない。

## Q04の検査と未達

tests/material_forces.rsでは同じcheckpointから分岐させたWorldについて、共有予約が不要な構成（力学DDA＋粒子、または圧力＋scalar＋粒子）で既存個別solverと統合APIを比較し、各report・checkpoint byte列の一致を検証する。圧力＋scalar＋粒子の組合せは4tick連続で個別参照経路と統合APIのreport・完全checkpointを照合する。同tickで力学DDAとscalarを併用した場合は専用回帰により、DDAで動いた砂がscalarにもう一度移動されないことを確認する。合法な力学更新後のscalar候補上限失敗と、そのErrを呼び出し元が無視する場合でも原子rollbackになることを検査する。さらに二つのlayerで各々の正規粒子を一度だけ積分することを確認する。

追加の回帰試験では同layerの正規粒子の現在位置を囲んで、scalarとmotionがその空cellへ別の素材を侵入させず、別layerの粒子なら独立に通過できることを検証。非simulated layerに対するphaseと粒子限定入口はbyte単位のWorld rollbackを要求する。

tests/material_runtime.rsでは、Runtime Materials phaseの監査付きSystemから、Q16力学と標準scalarを同一取引に統合。3tickの粉体の落下、World/Runtimeの時刻、全表現収支、毎tick checkpoint→World::restore一致を検証する。

`WorldEdit::step_material_phase_with_scalar_sleep`は同じphase予約をsleep対応scalarへ渡し、trackerを値で返す。phase後段が失敗した場合、World候補とtrackerのどちらもcommitされない。`tests/material_scalar_sleep.rs`では封じ込めた粉体・液体・気体で8tick、通常phaseのreportと完全checkpointが一致し、最初の参照実行で証明を作った後の7tickがsleepを使うことを確認する。chunk局所sleepは候補の停止と標準scalarの1cell haloを検査し、隣接chunk内部の移動を許したままhalo侵入で起床する。さらに正規particle候補数の失敗をscalar処理後へ注入し、phase全体のcheckpoint rollbackを検査する。対象layerにparticleがある間は証明を無効にし、移動先占有の変化を追跡しなくてよい場合だけsleepする。trackerのcheckpoint復帰後は既存契約どおり一度参照経路で再検証する。

Runtimeの順序検証には、同じMaterials phase内で依存順とbarrierを明示した二つのSystemを追加した。前段Systemが理由付きSource、後段Systemが理由付きSinkを同じセルへ行い、同tickの台帳が2件のreceiptを正しい順序で持つことを確認する。後段の未読込セル編集が失敗した場合は、前段のSourceと台帳まで含めてRuntime tick全体が破棄される。

### PressureJob後の新snapshotから再探索するphase

`step_material_phase_with_pressure_job_search`はReady済みPressureJobを候補へ適用してから、新しい圧力fieldでPressurePushSearchを開始する。押出し開始時のlayer・source・`PressurePushConfig`・budgetは`MaterialPhasePressureSearchInput`へまとめて渡す。探索がbudget内に終わらない場合、pressure出力とpending searchをWorld候補へ残し、通常MaterialPhaseを保留する。呼出側はpending searchをWorld StateStoreへ保存し、checkpoint/Runtime candidateを通じて次のbarrier後に読み戻せる。`resume_material_phase_with_pressure_search`は次のbudgetを消費し、Searchingなら更新後のsearchを同じstore keyへ上書きする。Pressure出力後のchunk revisionを基準にJobを作るため、継続時に渡すMaterialMotionJobはpressure公開済みWorldから生成する。初回呼出では事前revisionのJobを受け付けない。

探索がReadyなら、押出し経路を標準phaseと共有するCellReservationsへ登録してからpressure公開後に作成したMaterialMotionJob・cell force+DDA・scalar・正規粒子DDAを一候補へ公開する。Jobのsource・経路・destinationも同じ予約へ入り、jobと押出しが独立していても後段solverがどちらも再移動しない。NoOutletなら押出しだけを省略し、標準phaseを実行する。terminalになった探索状態は`WorldEdit::remove_state`で通常作者stateから削除できる。MixtureStore・receipt・balance logはこの汎用削除口から削除できない。pressure出力、押出し、後段phase、作者Job状態の削除は同じ外側WorldEditに含められ、後段失敗は全体rollbackする。

探索中の各pollはpressure job出力scratchを使わず、budgetとnode容量・活動chunk数に応じてsearch node/visited scratchを使う。job workはPressurePushSearchが走査する全loaded chunk数を見積りへ含め、visited/search scratchはactive chunk数に比例する。連続予算はsearch node容量・chunk map走査・pressure検証とphase予約に比例し、固定上限は既存の`job_cells`/`job_bytes`と探索node上限に従う。毎tick全World複製は追加しない。実測benchmarkは未実施であり、性能改善は主張しない。
